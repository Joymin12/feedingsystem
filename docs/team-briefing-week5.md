# 5주차 담당 영역 브리핑

발표에서 자기 파트 질문을 받았을 때 답할 수 있도록, 영역별로 무엇을 만들었고 왜 그렇게 했는지 정리한 문서입니다.
각자 자기 항목만 읽어도 되지만, "왜 AI가 아니라 엔진인가"(공통) 부분은 모두 알고 있어야 합니다.

---

## 공통 — 모두가 알아야 할 한 가지

이번 주 핵심 메시지는 **"교정 계산은 엔진이, 설명은 AI가"** 입니다.

원래 5주차 계획은 AI가 교정안을 만드는 것이었는데, 4주차에 판정 로직을 만들면서 교정 계산까지 엔진으로 끝나버렸습니다.
그래서 AI를 계산에서 빼고 설명 역할로 옮겼습니다. 이유는 네 가지입니다.

1. **검증 가능성** — 엔진 결과는 다시 계산해 맞는지 확인할 수 있지만, AI 답변은 호출마다 달라 같은 검증이 어렵습니다.
2. **안전 한도** — 원료별 사용수준(먹여도 되는 상한)은 반드시 지켜야 하는데, 계산으로만 확실히 보장됩니다.
3. **재현성** — 같은 배합에 어제와 오늘 답이 다르면 농가가 신뢰하지 않습니다.
4. **수치 신뢰도** — 생성형 AI는 그럴듯한 숫자를 지어내는 특성이 있어 kg 단위 급여량을 맡기기 어렵습니다.

## 조원민 — 판정 기준과 검증

### 1) 성장단계별 판정 기준치 확립

3단계(육성기 / 비육전기 / 비육후기)마다 9개 영양소의 적정 범위와 주의 구간을 정의했습니다.
코드에서는 `StageCriteria`라는 구조체에 들어 있고, 화면 코드에는 기준값이 하드코딩되어 있지 않습니다.
기준이 바뀌어도 이 한 곳만 고치면 앱 전체에 반영됩니다.

판정은 5개 구간으로 나뉘며 경계가 겹치지 않습니다.

```
부족 | 주의 | 적정 | 주의 | 과잉
```

### 2) 농사로 사용수준 데이터 수집 (24종)

농촌진흥청 농사로에서 한우 기준 원료별 사용수준을 수집해 데이터로 만들었습니다.
원문 그대로 `docs/seeds/hanwoo-usage-levels.json`에 보존하고, 앱에서 쓰는 형태로 `IngredientUsageLimits.swift`에 구조화했습니다.

대표 사례:

| 원료 | 육성기 | 비육기 | 근거 |
|---|---|---|---|
| 맥주박 | 20% 미만 | 후기 10% 이내 | 비육 후기 섭취량 저하 |
| 미강, 쌀겨 | 20% 이하 | 10% 이하 | 연지방 축적, 체지방 황색화 |
| 채종박 | 7% 이내 | 7% 이내 | 반추동물 제한 |
| 주정박 | 농후사료의 5% 이하 | 농후사료의 5% 이하 | 다량 급여 시 기호성 저하 |

단계별로 한도가 다른 원료가 있어서(맥주박, 미강), 성장단계에 따라 다른 값이 적용되도록 했습니다.

### 3) 항목별 중요도(가중치) 설계

9개 영양소를 똑같이 취급하지 않고, 어긋났을 때의 위험도에 따라 가중치를 다르게 뒀습니다.

| 영양소 | 가중치 | 이유 |
|---|---|---|
| CP, TDN | 2.5 | 증체를 좌우하는 핵심 |
| Ca:P 비율 | 2.0 | 요결석 위험 |
| EE(조지방) | 1.5 | 반추위 기능 저해 |
| Ca, P | 1.2 | 골격 형성 |
| NDF, ADF | 1.0 | 유효섬유, 산증 위험 |
| 수분 | 0.8 | 섭취, 저장 문제라 후순위 |

### 4) AI 응답 검수 기준

AI 설명이 사양학적으로 틀린 말을 하지 않는지 검수하는 기준을 세웠습니다.
"부족한 항목을 채운다면서 그 성분이 없는 원료를 늘리라고 하지 않는가", "반추위 적응 안내가 빠지지 않았는가" 같은 항목입니다.

### 예상 질문

**Q. 기준치는 어디서 가져왔나요?**
> 한국가축사양표준과 전문가 자문을 바탕으로 정리했습니다. 사용수준은 농촌진흥청 농사로에서 직접 수집했습니다.

**Q. 가중치 2.5, 2.0 같은 숫자는 근거가 있나요?**
> 문헌에서 인용한 값은 아닙니다. 병으로 이어지는 항목과 증체에 직결되는 항목을 앞에 둔다는 원칙으로 저희가 정한 설계값이고, 전문가 자문을 통해 조정할 계획입니다. 솔직히 이 부분은 앞으로 다듬어야 할 부분입니다.

**Q. 왜 '주의' 구간을 따로 뒀나요?**
> 기준을 조금 벗어난 것과 크게 벗어난 것을 같게 표시하면 농가가 우선순위를 못 정합니다. 당장 손봐야 하는 것과 지켜봐도 되는 것을 구분하기 위해서입니다.

## 방덕재 — 프론트엔드 (앱 화면)

### 1) AI 설명 화면 구현

추천안 화면 하단에 "AI 설명" 카드를 만들었습니다. 상태가 네 가지입니다.

| 상태 | 화면 |
|---|---|
| 대기 | "AI 설명 보기" 버튼 |
| 로딩 | 스피너 + "설명을 만드는 중입니다…" |
| 완료 | 설명 문장 + "수치와 판정은 계산 엔진이 확정한 값이며, AI는 이를 인용해 설명만 합니다" |
| 실패 | 안내 문구 + "다시 시도" 버튼 |

실패 상태를 **오류 화면으로 만들지 않은 것**이 핵심입니다. 빨간 에러 대신 파란 안내로 두고, 아래 "왜 이렇게 추천했나"(앱 내장 설명)로 유도합니다.

파일: `RecommendationViews.swift`

### 2) 증감 조정안 표시 개선

원료별로 증감량만 보여주면 농가가 "그래서 몇 킬로를 넣으라는 거지?"를 직접 계산해야 합니다.
그래서 **기존 kg과 적용 후 kg을 함께** 표시하도록 했습니다.

```
루핀씨드
3kg → 7.0kg              +4.0kg
```

접근성 라벨도 함께 넣어서, 화면을 읽어주는 기능을 쓸 때 "루핀씨드 3킬로그램에서 7킬로그램으로 증량"으로 읽히도록 했습니다.

### 3) 판정 결과 화면

영양소별로 현재값, 기준 범위, 판정(과잉/적정/주의/부족), 설명 문구를 보여줍니다.
**색상과 아이콘을 화면 코드에 직접 넣지 않고** 판정 결과에서 계산해 오도록 했습니다. 기준이 바뀌어도 화면을 고칠 필요가 없습니다.

### 4) 사용수준 안내를 kg으로 환산해 표시

농사로 사용수준은 "전체 사료의 10% 이내" 같은 비율로 되어 있는데, 농가는 kg으로 계량합니다.
그래서 화면에서는 **"조정 후 7.0kg — 육성기 사용수준 상한(총량의 10% = 최대 3.6kg) 이내입니다"** 처럼 kg으로 환산해 보여줍니다.

### 예상 질문

**Q. 서버가 죽으면 앱이 어떻게 되나요?**
> 화면이 깨지지 않습니다. AI 설명 자리가 안내 문구로 바뀌고, 그 아래 내장 설명으로 근거를 확인할 수 있습니다. 계산과 판정, 교정안은 앱 안에서 이뤄지므로 그대로 나옵니다.

**Q. 왜 증감량만 보여주지 않고 전후를 다 보여주나요?**
> 증감량만 보면 농가가 최종 투입량을 암산해야 합니다. 계량기 앞에서 쓰는 화면이라 최종 숫자가 바로 보여야 한다고 봤습니다.

**Q. 로딩이 오래 걸리면요?**
> 현재 10초 내외입니다. 스피너와 안내 문구를 띄우고, 50초까지 기다린 뒤 실패로 처리해 폴백합니다.

## 배성준 — 백엔드 (서버 구축, Gemini 연동)

### 1) 설명 API 서버 구현

NestJS에 `POST /v1/explanations` 엔드포인트를 만들었습니다.
앱이 엔진 판정 결과와 교정안을 JSON으로 보내면, 서버가 Gemini를 호출해 설명 문장을 돌려줍니다.

파일: `apps/api/src/explanations/` (컨트롤러, 서비스, DTO, Gemini 클라이언트)

**앱이 구글을 직접 호출하지 않는 이유**는 API 키 때문입니다. 앱 번들에 넣은 키는 추출될 수 있어서, 키는 서버 환경변수(`.env`)에만 두고 앱은 우리 서버만 바라봅니다. `.env`는 `.gitignore`에 등록되어 git에 올라가지 않습니다.

### 2) Gemini 호출부

SDK 대신 REST를 직접 호출했습니다. 의존성이 하나 줄고, 다른 AI로 바꿀 때 이 파일 하나만 고치면 됩니다.

```
모델          gemini-flash-latest (무료 티어)
temperature   0.3
topP          0.8
topK          20
maxOutputTokens 4096
타임아웃       40초
```

### 3) 연동 과정에서 해결한 문제 3가지

이 부분이 실제로 시간을 가장 많이 쓴 곳이고, 질문받기 좋은 지점입니다.

**모델 이름이 404** — 처음에 `gemini-2.5-flash`로 지정했더니 "신규 사용자에게는 더 이상 제공되지 않는다"며 404가 났습니다. 사용 가능한 모델 목록을 조회해서, 버전 고정 이름 대신 별칭인 `gemini-flash-latest`로 바꿔 해결했습니다.

**응답이 중간에 잘림** — 최신 Gemini는 답변 전에 '생각'하는 단계가 있는데, 그 토큰이 출력 예산에 포함됩니다. 처음 1024로 잡았더니 생각하는 데 다 쓰여 61자에서 잘렸습니다. 생각을 끄는 설정은 이 모델에서 400 오류가 나서, 출력 예산을 4096으로 올려 해결했습니다.

**타임아웃이 너무 짧음** — 15초로 잡았는데 실제 응답이 12~13초라 아슬아슬하게 실패했습니다. 40초로 늘렸습니다.

### 4) 비용 관리

무료 티어 한도 내에서 쓰고, 호출은 추천 결과당 1회로 제한했습니다.
결제 계정을 연결하지 않았기 때문에 한도를 넘어도 과금되지 않고 429(할당량 초과) 오류가 나며, 이 경우 앱은 폴백으로 넘어갑니다.

### 예상 질문

**Q. API 키가 유출되면요?**
> 앱에는 키가 없습니다. 서버 환경변수에만 있고 git에도 올라가지 않습니다. 유출 시에는 구글 콘솔에서 키를 폐기하고 새로 발급하면 됩니다.

**Q. 비용이 얼마나 드나요?**
> 무료 티어 안에서 쓰고 있어 현재 0원입니다. 결제 수단을 연결하지 않아서 한도를 넘겨도 요금이 발생하지 않고 오류로 처리됩니다.

**Q. 다른 AI로 바꿀 수 있나요?**
> 서버의 호출부 파일 하나만 교체하면 됩니다. 앱과 프롬프트는 그대로 둘 수 있는 구조로 만들었습니다.

## 이상혁 — 백엔드 (프롬프트 설계, 응답 검증)

### 1) 시스템 프롬프트 설계

AI가 매번 지켜야 할 규칙을 시스템 프롬프트로 고정했습니다. 크게 금지 규칙과 형식 규칙입니다.

**금지 규칙**
- 수치를 새로 계산하거나 추정하지 마라
- 입력에 없는 숫자를 쓰지 마라
- 부족/주의/적정/과잉 판정을 번복하지 마라
- 배합에 없는 원료의 투입량을 제시하지 마라

**형식 규칙**
- 번호와 제목 없이 한 문단으로
- 전체 4문장을 넘기지 마라
- 첫째 무엇이 기준을 벗어났는가 / 둘째 어떤 원료를 왜 늘렸는가 / 셋째 어떤 원료를 왜 줄였는가 / 넷째 2~3주에 걸쳐 나누어 적용하라

### 1-1) 튜닝 과정 — 실제로 무엇을 고쳤나

"프롬프트 튜닝"이 구체적으로 무엇이냐는 질문을 받을 수 있습니다.
**응답을 받아보고, 문제를 찾고, 규칙을 추가해 다시 받아보는 것을 반복했습니다.** 네 번 고쳤습니다.

**1차 — 길이 문제**

처음에는 5단 구조(핵심 문제 / 1차 조정 / 교차 영향 / 2차 보완 / 기대 결과)로 설계했습니다.
실제로 받아보니 582자가 나왔고, 앱 카드 한 화면에 들어가지 않아 스크롤해야 했습니다.
축사에서 읽는 글로는 너무 길다고 판단해 **4문장 제한**으로 바꿨습니다. 결과는 210자로 줄었습니다.

**2차 — 무엇을 말할지 좁히기**

길이만 줄이니 이번에는 내용이 두루뭉술해졌습니다. "영양 균형이 개선됩니다" 같은 일반론이 들어갔습니다.
그래서 **"왜 늘리고 왜 줄였는가에만 답하고, 배경 설명이나 일반론은 쓰지 마라"**를 넣었습니다.
문장별 역할도 지정했습니다. 첫째 문장은 무엇이 벗어났는가, 둘째는 왜 늘렸는가, 셋째는 왜 줄였는가, 넷째는 적용 시 주의.

**3차 — 원료 나열 문제**

조정 원료가 5~6개일 때 전부 나열해 문장이 다시 길어졌습니다.
**"늘리고 줄인 원료가 여러 개면 가장 변화가 큰 것만 언급하라"**를 추가했습니다.

**4차 — 영양소 용어 오기 (가장 중요)**

받아본 응답에 이런 문장이 있었습니다.

> "단백질 12.6, **난소화성섬유소** 17.8, 칼슘 0.1은 부족 판정을 받았고 ... **가가용무질소물** 74.7은 과잉"

ADF를 "난소화성섬유소", TDN을 "가가용무질소물"이라고 불렀는데 **둘 다 틀린 용어입니다.**
TDN은 가소화영양소총량이고, 가가용무질소물이라는 말은 존재하지 않습니다.
숫자는 맞는데 이름을 지어낸 것이라 기존 검증 장치로는 걸러지지 않았습니다. 전문가가 보면 바로 지적당할 부분입니다.

그래서 **"영양소 이름은 입력에 적힌 표기(CP, TDN, ADF)를 그대로 쓰고, 풀어 쓸 때는 단백질·에너지·섬유소처럼 농가가 쓰는 말만 써라. 전문 용어를 새로 지어내거나 바꿔 부르지 마라"**를 추가했습니다.

수정 후 응답입니다.

> "현재 CP, ADF, Ca는 부족하고 TDN은 과잉이며 NDF는 주의 단계에 있습니다. 부족한 ADF(섬유소)를 채우기 위해 섬유소가 풍부한 볏짚(사일리지)을 가장 크게 늘렸습니다. ..."

이 밖에 마크다운 강조 기호(`**조사료**`)가 그대로 화면에 노출되는 문제가 있어 **"표나 마크다운 기호를 쓰지 마라"**도 넣었습니다.

### 2) 응답 검증 장치 (가드레일)

AI 응답을 그대로 화면에 보여주지 않고, 기계적으로 세 가지를 검사합니다.
하나라도 걸리면 응답을 버리고 앱이 내장 설명으로 폴백합니다.

| 검사 | 방법 |
|---|---|
| 수치 창작 | 응답에 나온 숫자가 엔진이 보낸 값에 없으면 차단 (단 12 이하 정수는 "2~3주" 같은 서술이라 허용) |
| 판정 번복 | 엔진이 '부족'이라 한 항목을 '적정'이라 말하면 차단 |
| 원료 창작 | kg 수치 앞 40자 안에 배합에 있는 원료명이 없으면 차단 |

파일: `apps/api/src/explanations/guardrails.ts`

### 3) 검증 장치의 테스트

가드레일이 제대로 동작하는지 확인하는 테스트를 5개 만들었습니다.

- 엔진 값만 인용한 정상 설명은 통과하는가
- 없는 숫자("일당증체량 0.95kg")를 지어내면 걸러내는가
- 판정을 뒤집으면("CP는 적정합니다") 걸러내는가
- 배합에 없는 원료("석회석을 2.0kg 추가")를 제시하면 걸러내는가
- 적정 항목을 적정이라 말하는 정상 문장은 통과하는가

**이 테스트가 실제로 오탐을 하나 잡았습니다.** 처음에는 kg 앞 문자열을 원료명으로 인식했는데, "루핀씨드를 3kg**에서** 7.0kg으로"에서 '에서'를 원료명으로 오인해 정상 응답을 거부했습니다. kg마다 앞 구간을 훑어 아는 원료명이 있는지 확인하는 방식으로 바꿔 해결했습니다.

### 4) 폴백 설계

서버 없음, 키 없음, 네트워크 끊김, AI 응답이 검증 실패 — 이 네 가지를 앱 입장에서 모두 같은 결과로 처리하도록 했습니다.
원인이 달라도 사용자에게 필요한 건 "지금은 AI 설명을 못 쓰지만 근거는 볼 수 있다"는 사실 하나이기 때문입니다.

### 예상 질문

**Q. AI가 거짓말을 하면 어떻게 걸러내나요?**
> 응답에 나온 숫자가 엔진이 보낸 값에 있는지 하나하나 대조합니다. 없는 숫자가 나오면 그 응답을 버리고 내장 설명으로 대체합니다. 판정을 뒤집는 표현과 배합에 없는 원료 언급도 같은 방식으로 막습니다.

**Q. 검사에서 걸리면 사용자는 어떻게 되나요?**
> 오류를 보여주지 않고 앱 내장 설명으로 조용히 바뀝니다. 사용자 입장에서는 AI 설명이 안 나온 것뿐이고, 추천 내용은 그대로 볼 수 있습니다.

**Q. 왜 4문장으로 제한했나요?**
> 처음에는 5단 구조로 길게 썼는데, 축사에서 읽기엔 너무 길었습니다. 농가에 필요한 건 "왜 이걸 늘리고 저걸 줄였는가"이지 배경 설명이 아니라고 판단해서 그 이유에만 답하도록 고정했습니다.

**Q. 프롬프트 튜닝이라는 게 정확히 뭘 하신 건가요?** (핵심 질문)
> 응답을 받아보고 문제를 찾아 규칙을 추가하는 걸 네 번 반복했습니다. 처음엔 582자로 너무 길어서 4문장으로 줄였고, 그러자 일반론이 들어가서 "왜 늘리고 줄였는지에만 답하라"로 좁혔습니다. 원료를 다 나열해서 "가장 변화가 큰 것만 말하라"를 넣었고, 마지막으로 AI가 영양소 이름을 잘못 부르는 걸 발견해서 표기를 고정했습니다. 결과적으로 582자에서 210자로 줄었습니다.

**Q. 영양소 이름을 잘못 부른다는 게 무슨 뜻인가요?**
> AI가 ADF를 "난소화성섬유소", TDN을 "가가용무질소물"이라고 썼습니다. 둘 다 없는 용어거나 틀린 이름입니다. 숫자는 맞았기 때문에 저희 검증 장치로는 걸러지지 않았고, 사람이 읽어보고 발견했습니다. 그래서 입력에 적힌 표기를 그대로 쓰라는 규칙을 추가했습니다. 자동 검사만으로는 부족하고 사람이 읽어봐야 하는 부분이 있다는 걸 확인한 사례입니다.

## 발표 중 서로 참고할 사항

- **숫자를 묻는 질문**은 조원민에게 (기준치, 사용수준, 가중치)
- **화면 동작을 묻는 질문**은 방덕재에게 (폴백 시 어떻게 보이나, 왜 이렇게 표시하나)
- **연동, 비용, 보안 질문**은 배성준에게 (키 관리, 무료 티어, 모델 선택)
- **AI가 틀리면 어떻게 하나**는 이상혁에게 (가드레일, 프롬프트, 폴백)

모르는 질문이 오면 추측하지 말고 "그 부분은 확인해서 다음 주에 보고드리겠습니다"라고 하는 편이 낫습니다.
특히 가중치 근거와 기준치 출처는 아직 전문가 자문으로 다듬어야 하는 부분이라, 확정된 것처럼 말하지 않는 게 안전합니다.
